About this data

  • Source. Everything here was pulled live from four Commslayer accounts on one login — Simply Elsie (7356, UK), Maggies Tanks (6576, US), Mary's Tanks (6377, AU) and Lyn's Tanks (6527, NZ) — via the Commslayer MCP API. Nothing is simulated. A fifth account, Mary and James (6570), was deliberately excluded.
  • Coverage. The two layers answer different questions and must not be mixed: layer one tells you how much of each issue there really is, layer two lets you read what customers actually wrote. Retrieval depth in layer two is uneven by design — Maggies Tanks alone runs over 1,300 tickets a day, far beyond what can be read ticket by ticket — so layer two percentages describe the retrieved set, not the business.
  • Brand comparison basis. Section 1 is fixed to 11–17 August because the reporting endpoints return one aggregate per window; it does not follow the date filter above, which drives layer two only. The final day is partial in every brand (data pulled mid-morning UTC on the 17th), which is why every brand's last point drops. Mary's Tanks reports in UTC+10, so its day boundaries differ by ten hours from the other three.
  • Classification. Primary issue category and sub-issue were assigned by reading each customer's actual message text, not by reusing Commslayer's labels. Categories beyond the requested list were added where the data demanded them — Product Usage / Difficult to Put On, Brand Trust / Provenance Doubt, Order Lookup / Account Data Error and Spam / Solicitation each recur often enough to stand alone.
  • Fields shown as "Not Available". Commslayer exposes no SKU field, and its conversation custom-attribute store is empty for this account, so SKU is unavailable for every ticket. Product, variant, size and colour are populated only where the customer stated them or where an order-confirmation or refund email was quoted inside the thread. Nothing has been inferred.
  • Resolution timing. Commslayer's API returns created_at and last_activity_at, but no explicit resolved-at timestamp. Resolution time and "date resolved" therefore use last activity on tickets whose status is resolved, which is an upper bound on the true handling time.
  • Statuses. Commslayer uses open, pending, snoozed and resolved. This account currently runs zero pending tickets; snoozed is the state the AI agent parks a thread in while waiting on a customer, so snoozed tickets are counted as unresolved throughout.
  • Date presets. "Today" is anchored to the most recent ticket in the dataset (), in UTC, matching the account's timezone. Period-over-period comparisons are suppressed rather than estimated when the prior period falls outside the retrieved window.
